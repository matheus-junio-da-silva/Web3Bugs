## Report verification conditions — LaunchEvent (pages 5–15)

The report specifies four mutually exclusive modeled states from `pair` and `stopped`: `open` (`pair == 0 && !stopped`), `closed` (`pair != 0 && !stopped`), `openStopped` and `closedStopped`. These predicates are distinct from `currentPhase`, the time-based phase enum. The source rules in `LEValidStates.spec`, `LEVarTran.spec`, `LEHighLevel.spec` and `LaunchEvent.spec` overlap by name but also differ in naming, conditioning or observation. Each must be assessed on its full body before transferring a historical result.

LaunchEvent verification assumptions explicitly include loops bounded to one iteration, correct WAVAX behavior, nonmalicious libraries, an initialized LaunchEvent, contemporary joe-core Router/Factory/rJOE implementations, and a harness for `_safeTransferAVAX` that the report says may **miss reentrancy**. The report describes properties of issuer allocations, user balances, timelocks, reserve balances, incentive accounting, LP withdrawals, valid-state transitions, deposit/withdraw additivity, noninterference and owner-only stopping. Report-level checkmarks apply to their actual reported conditions on the audited configuration, not to every similarly named snapshot rule.

## Report verification conditions — RocketJoeStaking (pages 16–21)

The report covers staking JOE custody and per-user stake sums, mutation authorization for `userInfo.amount` and `rJoePerSec`, pending rewards, emission timing, additivity and noninterference of deposits and withdrawals, and unit-test-style postconditions. It qualifies the initialization invariant, assumes initialized state for certain conditions, and says `verify_emergencyWithdraw` could not independently prove its nonreversion assertion; assuming nonreversion enabled the other checks. It also says some reward-timing claims were weakened due to timeouts. The source `Staking.spec` includes commented, not active, candidate rules named `updatePool_increases_accRJoePerShare`, `rJoe_solvency`, and `stake_duration_correlates_return`, matching the report's not-fully-implemented section; these are not catalogued as active.

## Attribution protocol

Individual examples in `results/spec/incomplete/24` state whether the *exact source property* is listed and checked in the report. A PDF ✓ supports `VERIFIED` only when its full condition, target, and setup match the source instance; otherwise the result is `NOT_STATED`. Neither an aggregate declaration of system correctness nor a report-level finding should automatically change `Detection Outcome` for a different rule.

## Source vs. printed verification formulas — explicit exceptions

- **`LEHighLevel.spec::hl_depositAdditivity`**: PDF p. 13 uses matching senders; the source requires two *different* senders and additionally compares initially equal user balances. These are materially different relational tests. Example 2 `NOT_STATED`.
- **`LEHighLevel.spec::hl_noDepositFrontRun`**: PDF p. 14 prints `userBalanceBefore - amount`, whereas the source checks `userBalanceBefore + e.msg.value` after deposit. Example 5 `NOT_STATED`.
- **`LEHighLevel.spec::hl_withdrawAdditivity`**: PDF p. 13 and source both compare single withdrawal `x` to sequential `y+z` via user balance, so example 3 `VERIFIED` historically, subject to assumptions.
- **`Staking.spec::RJPS_only_owner_and_function`**: PDF p. 18 prints `userBalance_pre/post` instead of the source's `RJPS_pre/post`, making a literal condition comparison ambiguous. Example 150 `NOT_STATED` pending provenance.
- **`Staking.spec::balanceOf_Joe_eq_totalJoeStaked`**: PDF p. 17 uses equality `==` but source example 147 uses `>=`; it remains `NOT_STATED`.
