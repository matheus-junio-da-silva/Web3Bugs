# Formal Verification of Aave Protocol V3

> **Historical transcription (Markdown)** of Certora's January 2022 Aave V3 report.
> Original PDF: [AaveV3Jan2022-1.pdf](../resources/7/AaveV3Jan2022-1.pdf).
> Content and mathematical notation follow the report; PDF formatting, line wrapping, colored severity labels and hyperlink presentation are normalized in this Markdown view. The original PDF is authoritative for exact typography.
> **Do not confuse the January 2022 report's verified commit `a87d546` with the later PropertyGPT contract snapshot.** This transcription does not rerun Certora.

## Summary

This document describes the specification and verification of Aave's V3 protocol using the Certora Prover. The work was undertaken from Nov. 12, 2021 to Jan. 24, 2022. The latest commit reviewed and run through the Certora Prover was [`a87d546`](https://github.com/aave/aave-v3-core/commit/a87d546d57d4e49bcb450d3c46b50d6bc6e5ddee).

The scope comprised **StableDebtToken.sol**, **VariableDebtToken.sol**, **AToken.sol**, **ReserveConfiguration.sol**, **UserConfiguration.sol**, and partial verification of **Pool.sol**, with original proof-result links in the [published report](https://hackmd.io/Do1H0F5SRhiQjxUVIlN1qA).

The Certora team used formal specifications and performed a manual audit. Tokenization rules included ERC20-oriented and Aave V2-derived properties; the Pool analysis focused on reserve data, EMode classification, and compatibility with user operations after modular verification of the configuration libraries.

## List of Main Issues Discovered

### Critical — Loss of assets

- **Description:** `repayWithATokens` lacked a health-factor check, allowing repayment to release liquidity without proper collateral accounting.
- **Mitigation/Fix:** Disallowed repayment with ATokens on behalf of another user.
- **Property violated:** *Any Operation Should Preserve User's HF > 1.*

### High — Risk Exposure

- **Description:** `AToken.transfer()`, liquidation and `mintUnbacked()` could leave a user with isolated and non-isolated collateral simultaneously, bypassing a debt ceiling.
- **Mitigation/Fix:** Added an isolation-mode check to these functions.
- **Property violated:** *A User Can't Hold Both an Isolated and non-Isolated Assets as Collaterals.*

### High — Loss of assets

- **Description:** Liquidations confused ordinary asset price feeds with EMode price feeds.
- **Mitigation/Fix:** Price sources were chosen according to EMode.
- **Property violated:** *EMode source price usage.*

### Medium — Loss of Users' Profitability

- **Description:** EMode liquidation could use the incorrect liquidation bonus.
- **Mitigation/Fix:** Awarded the correct EMode liquidation bonus.

### Medium — Loss of revenue

- **Description:** `repayWithATokens` updated interest rates as though the repayment added underlying liquidity. No underlying liquidity was actually added, permitting manipulation of rates.
- **Mitigation/Fix:** Rate updating was changed to pass zero added liquidity.
- **Rule coverage:** *No Change in Underlying's Balance Implies No Change in rate.*

### Low — Integrity of ReserveList

- **Description:** `_addReserveToList` inserted a new reserve into every empty location of the reserve list, rather than just the first.
- **Mitigation/Fix:** Added a `return` within the loop.
- **Rule coverage:** *The same asset should not appear twice on the reserves list.*

### Recommendation — Denial of Service

- **Description:** Through `supply()` and `AToken.transfer()`, other users could force an account into isolation mode and temporarily block further borrowing.
- **Mitigation/Fix:** The user can withdraw the isolation-mode asset.
- **Property violated:** *Informative Rule: Check which functions can revert for one user due to another user's action.*

## Overview of the verification

### Description of the system

Aave is a decentralized, non-custodial liquidity-market protocol. Suppliers provide liquidity to earn income, while borrowers borrow under either overcollateralized (perpetual) or undercollateralized (one-block) conditions.

### Description of the specification files

Six specifications were described: three tokenization specs, the Pool spec, the ReserveConfiguration spec, and the UserConfiguration spec. Tokenization specifications draw on ERC20 verification experience. The Pool work tests reserve data, EMode classification, and user actions through modular library verification.

## Assumptions and Simplifications

- Accumulation rates were assumed to be **1**: no interest accumulates.
- Hashes were arbitrary but deterministic.
- Loops were unrolled; violations requiring more than one loop iteration could be missed.
- External calls could have arbitrary effects outside the verified contract, but were assumed not to modify its internal state; some reentrancy vulnerabilities might be missed.
- The incentives controller was not used.

## Verification Conditions

### Notation

**✔** designates a rule formally verified at the last reviewed commit, subject to report footnotes and assumptions. The report expresses conditions as formulas or Hoare triples `{p} C {q}`. Formula conditions must hold in every reachable state; a triple asserts that any non-reverting execution of `C` satisfying `p` ends in a state satisfying `q`. `C@withrevert` also considers reversion. Undefined variables denote arbitrary values. Some getters are supplied by harnesses or definitions rather than contract ABI.

### Stable-Debt Token — Rules

1. **Integrity of User's Time-Stamp ✔**: `getUserLastUpdated(user) <= currentBlock.timestamp`.
2. **Any Operation Changes At Most One User's balance ✔**: Given distinct accounts A, B and their prior balances, for arbitrary operation `op`, at least one of `balanceOf(A)`, `balanceOf(B)` is unchanged.
3. **Change in Total Supply iff an Equal Change in Some User's Balance ✔**: If a user's balance changes across `op`, its change equals the total-supply change (using the report's subtraction formula).
4. **Additivity of Burn ✔**: `burn(user,x); burn(user,y)` is equivalent to `burn(user,x+y)` in the same transaction.
5. **Integrity of Mint ✔**: `{b == balanceOf(user)} mint(delegatedUser,user,x,index) {balanceOf(user) == b + x}`.
6. **Integrity of Burn ✔**: `{b == balanceOf(user)} burn(user,x) {balanceOf(user) == b - x}`.
7. **Invertibility of Mint and Burn ✔**: Minting and then burning the same amount for a user preserves the original `balanceOf(user)`.

### Variable-Debt Token — Rules

1. **Any Operation Changes At Most One User's balance ✔**: With distinct A and B, any operation leaves at least one of their balances unchanged.
2. **Change in Total Supply iff an Equal Change in Some User's Balance ✔**: A change to a user balance equals the total-supply change.
3. **Only pool can change total supply with burn and mint ✔**: When `op` changes supply, its caller must be the pool and `op` must be `mint` or `burn`.
4. **Mint and burn are inverse operations ✔**: `mint(delegatedUser,user,amount,index); burn(user,amount,index)` preserves the original user balance.
5. **Additivity of burn ✔**: Two burns of x and y equal one burn of x+y at the same timestamp.
6. **Integrity of mint ✔**: Minting x increases the user balance by x.
7. **Burn doesn't change other's balance and data ✔**: For other ≠ user, `burn(user,amount,index)` preserves `balanceOf(other)`.
8. **Mint doesn't change other's balance and data ✔**: With other ≠ user, minting preserves the other's balance; when user ≠ onBehalfOf the user's prior balance is also preserved.
9. **Burn zero doesn't change balance ✔**: `burn(user,0,index)` preserves the user's balance.

### AToken — Rules

1. **Any Operation Changes At Most Two User's balance ✔**: For three distinct accounts A, B, C, any operation must leave at least one balance unchanged.
2. **Integrity of mint ✔**: Minting x increases balance by x, with error bounded by ε.
3. **Additivity of mint ✔**: `mint(u,x);mint(u,y)` is approximately equal to `mint(u,x+y)`, within ε.
4. **Mint of zero is not possible ✔**: If `amount == 0`, mint must revert.
5. **Integrity of transfer ✔**: (I) A transfer between distinct addresses decreases the sender's and increases the recipient's balance within ε; (II) the underlying ERC20 balance remains unchanged.
6. **Additivity of transfer ✔**: Two transfers of x, y and a one-step transfer of x+y preserve analogous sender/recipient results within 3ε subject to the report's account-separation and equal-prebalance assumptions.
7. **Integrity of burn ✔**: Burning x reduces the user's AToken balance within ε and, when receiver ≠ AToken, increases the receiver's underlying balance by x within ε.
8. **Additivity of burn ✔**: Two burns of x and y equal one burn of x+y at the same timestamp.
9. **Burn doesn't change other's balance and data ✔**: With other different from burn user and receiver, the other's balance and additional data are unchanged.
10. **Mint doesn't change other's balance and data ✔**: For other different from the mint beneficiary, the other's balance and additional data are unchanged.

> The report numbers both 'Mint of zero' and 'Integrity of transfer' as item 4; this transcription retains the logical sequence without concealing the numbering error.

### ReserveConfiguration — Rules

1. **Integrity Setters/Getters ✔**: For an arbitrary configuration member x, `setX(r,y)` must yield `getX(r) == y`.
2. **Each setter changes only one member ✔**: `setX(r,y)` preserves the prior value of each other member x′.

These are **aggregate report assertions**. They are not individual verdicts for every setter rule in the PropertyGPT snapshot.

### UserConfiguration — Rules

1. **Consistency of isEmpty ✔**: `isEmpty => !isBorrowingAny() && !isUsingAsCollateralOrBorrowing(reserveIndex)`.
2. **Consistency of not isEmpty ✔**: `(isBorrowingAny() || isUsingAsCollateral(reserveIndex)) => !isEmpty()`.
3. **Consistency of isBorrowingAny ✔**: `isBorrowing(reserveIndex) => isBorrowingAny()`.
4. **Consistency of isUsingAsCollateral functions ✔**: `(isUsingAsCollateral(reserveIndex) || isBorrowing(reserveIndex)) <=> isUsingAsCollateralOrBorrowing(reserveIndex)`.
5. **Integrity of User's Isolation mode configuration data ✔**: `!isUsingAsCollateralOne() => !isIsolated()`.
6. **Integrity of setBorrowing ✔**: Given reserveIndex < 128, `setBorrowing(reserveIndex,borrowing)` implies `isBorrowing(reserveIndex) == borrowing`.
7. **Integrity of setUsingAsCollateral ✔**: Given reserveIndex < 128, setter result equals `isUsingAsCollateral(reserveIndex)`.
8. **setBorrowing for one reserve doesn't affect others ✔**: For two distinct reserve indices < 128, setting one borrowing flag preserves both the borrowing and collateral flags of the other.
9. **setUsingAsCollateral for one reserve doesn't affect others ✔**: Analogous preservation of other-reserve flags for the collateral setter.

### Pool — Rules

1. **Integrity of Supply Cap ✔\*\***: AToken total supply must not exceed its reserve's supply cap. **The report states the rule times out for some functions.**
2. **Integrity of setUserEMode ✔**: Following `setUserEMode(category)`, the user's EMode category matches that value.
3. **User can always set own eMode to 0 ✔**: `setUserEMode(0)` does not revert.
4. **If borrow succeeds then reserve flags are correct ✔**: The reserve must be active, not frozen or paused, with borrowing enabled and, if stable-rate borrowing is selected, stable-rate borrowing enabled.
5. **reservesCount() is monotonic ✔**: Operations do not decrease the reserve count.
6. **Each function changes at most one configuration ✔**: For distinct reserve assets, an arbitrary operation leaves at least one reserve configuration unchanged.
7. **Reserve id always less than counter ✔**: If an index resolves to a nonzero reserve address, the index is below the reserve count.
8. **Bijective property of reserve id ✔**: For a nonzero token and nonzero index, token↔index lookups are equivalent; for index zero, the specified implication only applies one way.

> The original PDF's Pool rule numbering has gaps (1, 3, 4, 5, 6, 7, 8, 10). The numbering above is normalized for reading; **none of these Pool conditions is to be attached to the distinct active `pool.spec/getReserveNormalizedVariableDebtCheck` rule** without further report evidence.

### Stable-Debt Token — seven conditions

| Original # | Condition as reported (mathematical notation normalized) |
| --- | --- |
| 1 | \`getUserLastUpdated(user) <= currentBlock.timestamp\` |
| 2 | \`A != B && balanceA = balanceOf(A) && balanceB = balanceOf(B); op; balanceOf(A) == balanceA || balanceOf(B) == balanceB\` |
| 3 | \`balanceA = balanceOf(A), total = totalSupply(); op; balanceOf(A) != balanceA => balanceOf(A)-balanceA == totalSupply()-total\` |

| Original # | Condition |
