## Motivation

Check that the feed and optional bridge-wrapper mappings transition exactly as required for the three registry-management operations and remain unchanged for other methods.

## Reconstructed methodology

The following reasoning is reconstructed from the source property, available Solidity code, and the public report; it is not presented as private auditor reasoning.

1. Read the feed and bridge-wrapper addresses for a symbolic asset.
2. Select an arbitrary method; route the three registry-management selectors through call_f_with_params with controlled asset/feed/wrapper arguments.
3. Read both mappings again.
4. For ordinary enable, require the resulting feed to be nonzero and equal the supplied feed.
5. For wrapped enable, require both feed and wrapper to be nonzero and equal the supplied values.
6. For disable, require both values to be zero.
7. For every other selector, require both values to remain unchanged.

A counterexample would therefore show: one of those selector-specific state transitions does not match the assertion, or an unrelated method changes either mapping.

## Why the Solidity excerpt is relevant

ProofOfReserveAggregator stores the exact values observed by the property in _proofOfReserveList and _bridgeWrapperList (lines 17-21). The getters at lines 24-39 read those mappings. enableProofOfReserveFeed writes only the feed mapping at line 50; enableProofOfReserveFeedWithBridgeWrapper writes both mappings at lines 70-71; disableProofOfReserveFeed deletes both at lines 83-84. Those assignments correspond directly to the before/after values and selector-conditional assertions in the rule.
