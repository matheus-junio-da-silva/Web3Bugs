## Motivation

Verify the single-asset disable transition: inactive afterward, no length change if already inactive, and exactly one removal if previously active.

## Reconstructed methodology

The following reasoning is reconstructed from the source property, available Solidity code, and the public report; it is not presented as private auditor reasoning.

1. Require the array uniqueness and flag-consistency invariants through assetsRequirements.
2. Snapshot the selected asset flag and asset-array length.
3. Invoke disableAsset on the selected asset.
4. Read flag and length again.
5. Assert the flag is false; assert unchanged length if the asset was inactive; assert length decreased by one if it was active.

A counterexample would therefore show: disableAsset leaves the flag true, removes an already-disabled asset, or removes anything other than exactly one entry for an active asset.

## Why the Solidity excerpt is relevant

ProofOfReserveExecutorBase stores the list in _assets and membership flag in _assetsState (lines 24-28). disableAssets checks the flag, removes the address, and deletes the flag (lines 57-63); _deleteAssetFromArray performs the swap/pop removal (lines 71-84). The selected concrete target inherits this base implementation. These are the state/length transitions the rule observes; the missing single-asset harness is not reconstructed from them.
