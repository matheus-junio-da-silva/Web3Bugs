## Motivation

Verify the single-asset enable transition: active afterward, no duplicate insertion if already active, and exactly one addition if previously inactive.

## Reconstructed methodology

The following reasoning is reconstructed from the source property, available Solidity code, and the public report; it is not presented as private auditor reasoning.

1. Require the array uniqueness and flag-consistency invariants through assetsRequirements.
2. Snapshot the selected asset flag and array length.
3. Invoke enableAsset.
4. Read flag and length again.
5. Assert the flag is true; assert unchanged length if already active; assert length increases by one if previously inactive.

A counterexample would therefore show: enableAsset leaves the flag false, inserts another copy of an already-active asset, or fails to add exactly one entry for an inactive asset.

## Why the Solidity excerpt is relevant

ProofOfReserveExecutorBase stores the list in _assets and membership flag in _assetsState (lines 24-28). enableAssets checks the flag, pushes a previously disabled address, and sets its flag true (lines 46-54). The selected concrete target inherits this base implementation. These are the state/length transitions the rule observes; the missing single-asset harness is not reconstructed from them.
