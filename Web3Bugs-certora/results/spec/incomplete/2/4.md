## Motivation

Check idempotence of enabling the same asset and, specifically, that a duplicate asset address is not added on the second enable.

## Reconstructed methodology

The following reasoning is reconstructed from the source property, available Solidity code, and the public report; it is not presented as private auditor reasoning.

1. Require the array uniqueness and flag-consistency invariants.
2. Save the initial storage.
3. Execute enableAsset twice and record resulting membership and length.
4. Re-execute a single enableAsset from the saved initial storage.
5. Assert the twice-enabled state and length equal the once-enabled state and length.

A counterexample would therefore show: two enables from the same initial state produce a different membership flag or array length than one enable, which includes duplicate insertion of the asset identifier.

## Why the Solidity excerpt is relevant

ProofOfReserveExecutorBase stores the list in _assets and membership flag in _assetsState (lines 24-28). enableAssets checks the flag, pushes a previously disabled address, and sets its flag true (lines 46-54). The selected concrete target inherits this base implementation. These are the state/length transitions the rule observes; the missing single-asset harness is not reconstructed from them.
